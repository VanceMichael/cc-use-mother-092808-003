# 方案治理服务设计

面向研发中心的人工智能辅助造型方案治理。解决的具体问题：气动智能体把
仿真优化时间大幅缩短，但在进入全球产品网络前才发现——训练素材、提示、
供应商模型许可、设计师修改之间没有共同的版本记录，权属无法核对。

## 1. 任务目标与约束

| 业务约束（领域资料） | 服务目标 | 落地机制 |
| --- | --- | --- |
| 设计谱系 | 素材、模型、提示、候选、修改、合并可沿谱系回溯 | 候选携带叶子来源贡献向量与父代边，事件链记录全部派生 |
| 模型与素材许可 | 许可版本、收窄、到期、例外全程可核 | 许可版本化事件 + 评审时刻快照 + 职责分离审批 |
| 多目标评审 | 机器建议、人工选择、工程与审美取舍共同留痕 | 评审事件结构化记录 suggestions / decision / tradeoffs |
| 仿真回执 | 设备重传不重复记账，结果变化可拦截 | 会话幂等键 + 参数/摘要指纹 + 待查挂起状态机 |
| 量产冻结 | 量产前权属确认完整，冻结后版本不可变 | 冻结门（评审、权限、例外、核查）+ 谱系包哈希 |

贯穿性目标：

1. **统一版本记录**——上述所有事实进入同一条哈希链事件日志，不存在互
   不关联的多套台账；
2. **机密性**——机密项目的存在本身不向无关团队泄露（统一“不存在或无权
   访问”响应，不做存在性区分）；
3. **职责分离**——提交方案的人不能批准自己的许可例外；
4. **时间一致性**——许可收窄/到期对旧评审可验证、对新派生立即生效；
5. **重启可恢复**——评审期间进程重启，待办、到期许可、候选状态全部延续。

## 2. 总体架构：追加式事件日志 + 重放读模型

```
命令（登记/生成/派生/合并/评审/仿真/例外/冻结）
   │  规则校验（密级、职责分离、许可、状态机）
   ▼
AppendOnlyStore（JSONL，每条事件含 seq / ts / prev / hash）
   │  只追加、不修改、不删除
   ▼
GovernanceService 读模型（projects / grants / candidates /
   reviews / sim_sessions / investigations / exceptions / decisions）
   ▲
   └ 启动时重放全部事件重建；重启即恢复，没有日志之外的易失状态
```

事件结构（`src/governance/store.py`）：

```json
{
  "seq": 17,
  "ts": 40,
  "type": "SimulationAmended",
  "payload": { "...": "命令的完整事实" },
  "prev": "上一条事件的 sha256",
  "hash": "本条（除 hash 外）内容的 sha256"
}
```

- 任何对历史行的篡改都会在加载时断链，服务拒绝启动而不是静默截断；
- 事件时间戳与业务规则共用同一时钟源（可注入、可推进、不可回拨），
  加载历史日志后时钟自动对齐到最后事件时间；
- 单进程串行追加满足线性一致；多实例部署时把 `AppendOnlyStore` 换为
  同一抽象的事务性实现（如带行锁的事件表）即可，领域规则不变。

## 3. 统一版本登记的对象与事件

| 事件 | 登记内容 |
| --- | --- |
| `ProjectCreated` / `ClearanceGranted` | 项目密级、属主团队、获密级团队清单 |
| `ArtifactRegistered` | 素材权利来源 / 供应商模型 / 提示：标识、内容指纹、首版许可（同事件绑定，杜绝“素材在、许可不在”） |
| `LicenseNarrowed` | 许可新版本（权限只能是旧版子集，必须立即生效） |
| `CandidateGenerated` | 一次 AI 生成：模型 + 提示 + 素材、内容指纹、贡献向量、生成时许可 |
| `CandidateRefined` | 设计师人工修改：父代、修改说明、可选新增来源 |
| `CandidatesMerged` | 合并：父代权重、继承后的贡献向量与有效许可 |
| `ReviewRecorded` | 机器建议、人工决定、工程/审美取舍、权属确认、**当时许可快照** |
| `SimulationRecorded` / `SimulationAmended` | 设备、会话、参数指纹、摘要指纹、版本 |
| `InvestigationResolved` | 仿真核查结论与恢复 |
| `LicenseExceptionRequested` / `…Decided` | 许可例外申请与独立审批 |
| `ProductionFrozen` | 量产决定、谱系包哈希、链头锚点 |

## 4. 谱系与贡献分摊（`src/governance/lineage.py`）

**只追踪叶子来源。** 候选的贡献向量只保存素材/模型/提示这些叶子来源的
份额，派生与合并只组合向量，不把中间候选当来源：

- 连续派生 A→B→C 时，A 始终是一条来源、一份份额，不会因为多次派生被
  重复计算；
- 合并把父代向量按权重加权求和再归一化，同一来源经多条路径汇入时份额
  累加（这是它应得的总贡献），但仍是一个键；
- 菱形谱系（root→left/right→diamond）合并后，root 的来源各占其应有
  份额，不翻倍；
- 全部份额用 `Fraction` 精确表示并以 `"p/q"` 入日志，审计无浮点误差。

**许可继承 = 权限交集 ∧ 义务并集。** 候选的有效权限是所有来源当前权限
的交集；被收窄的权限同时记录 `restricted_by`（哪些来源造成限制），义务
（如署名）取并集继承。合并结果因此自动继承最严许可，例如供应商模型不
含 `publish`，任何并入它的候选都不能无例外发布。

## 5. 许可时间线：收窄、到期、例外

许可按来源保存为只增版本序列：

- **收窄**：新版本 `allows` 必须是当前版本的子集，且 `effective_from`
  不得晚于当前时间（不能预定未来“悄悄收窄”，收窄即生效）。旧版本原样
  保留。
- **新派生立即受限**：生成/派生/合并在落事件前按来源**当前**许可重算
  交集，缺 `derive`/`merge` 直接拒绝；许可到期同样即时生效。
- **旧评审按当时资料可验证**：评审事件内嵌快照——候选内容指纹、贡献向
  量指纹、每个来源当时的 `grant_id / version / terms_hash / allows /
  expires_at`。复核（`verify_review`）按快照里的版本号回查历史条款，
  即使该来源后来已收窄或到期，旧评审依然可核；快照与现状不符则复核
  失败。
- **许可例外**：申请产生待办，记录申请权限、理由、到期时间；审批强制
  职责分离（`requested_by ≠ decided_by`），且审批人须有项目密级。例外
  仅补权限、不抹限制，到期自动失效；量产时把有效例外一并固化进决定。

## 6. 保密模型

- 项目创建即标记 `confidential` 与属主团队，密级按团队授予；
- 所有读取与命令都经过 `_require_access`；
- 无密级访问（无论项目、候选、评审、来源是否存在）统一抛出
  “对象不存在或无权访问”，错误类型与“确实不存在”一致，从而无法通过
  报错差异探测机密项目或候选的存在；
- 审批、核查等跨团队动作要求先获得密级（如法务团队），无关团队连待办
  列表都无法触达。

## 7. 仿真回执：幂等与待查状态机

幂等键 = `device_id | session_id`，参数与摘要分别取内容指纹：

1. 首次上报：记 `SimulationRecorded`，发回执；
2. **完全相同的重传**：不新增事件，返回原回执（事件总数不变）——设备
   重传相同会话只记录一次；
3. **参数或摘要变化**：会话升版，记 `SimulationAmended` 并开出核查待办，
   把该候选及其全部后代停在 `suspended_pending_check`（已量产冻结的历
   史版本不回改）；
4. 待查期间禁止派生、合并、正式评审与量产；
5. 核查关闭后候选恢复到**最初被挂起之前**的状态；多个核查叠加时，只有
   覆盖该候选的全部核查都关闭才恢复。

## 8. 重启恢复

服务没有独立于日志的状态：重启 = 新建存储（加载并校验 JSONL）→ 重放
事件重建读模型。恢复内容包括：

- 候选生命周期状态（含待查及挂起前状态）；
- 待办：待批准的许可例外、未关闭的仿真核查、已到期/临期许可
  （`open_todos` 全部由状态派生）；
- 许可版本序列与到期判定（时钟对齐到历史事件，不倒退）；
- 恢复后可直接继续处理待办，且重复重启结果一致（重放确定性）。

## 9. 量产冻结与谱系终视图

量产批准的门禁顺序：未冻结 → 至少一条人工评审 → 未处于待查 → 无未关闭
的关联核查 → 当前许可或有效例外覆盖 `produce`、`publish`。

通过后记 `ProductionFrozen`（决定人、理由、权属确认、谱系包哈希、事件
链头锚点），候选进入不可变的 `production_frozen`：不能再次决定，也不能
继续派生。

`lineage(candidate_id)` 沿祖先闭包给出量产评审人需要的完整叙事：

- 节点与边：素材/模型/提示 → 机器生成候选 → 设计师修改 → 合并 →
  仿真回执 → 人工评审 → 量产决定；
- 每个候选的贡献分摊与当前有效许可、限制来源、继承义务；
- 评审中的机器建议、人工选择、工程取舍与审美取舍（各记选择与放弃项）、
  权属确认，以及快照是否仍可按当时版本验证；
- 经职责分离批准的许可例外（申请人与批准人分列）；
- 量产决定本身。

评审人因此可以沿谱系回答：“当前版本是如何由机器建议、人工选择、工程
与审美取舍以及权属确认共同形成的？”

## 10. 代码索引

- `src/governance/store.py`：时钟、追加式哈希链日志、加载校验；
- `src/governance/lineage.py`：贡献分摊、许可交集/义务并集、评审快照；
- `src/governance/service.py`：命令模型、读模型重放、密级与职责分离、
  仿真状态机、待办、量产冻结与谱系视图；
- `src/governance/errors.py`：保密、职责分离、许可、冲突等领域错误；
- `tests/test_governance_service.py`：逐场景测试（统一记录、去重分摊、
  菱形合并、保密、自批拒绝、收窄/到期、仿真幂等与待查、重启恢复、篡改
  拒绝、量产门禁与谱系包）。

## 11. 已知边界与后续取舍

- 当前持久化为单文件 JSONL，面向单节点治理；跨节点部署需替换为事务性
  事件存储，事件契约与规则层不变；
- 身份与团队密级假设由调用方（上游 IAM）注入，服务只做领域级判定；
- 内容指纹由上游提供（资产本体通常在对象存储/PLM 中），服务负责指纹与
  谱系、许可的绑定，不托管大体积资产；
- 许可例外目前按候选生效；若组织需要“来源级例外向下传播”，可新增事件
  类型而不改动既有谱系语义。
